# TableNest API reference

Base URL: `/api`. JSON in, JSON out. Interactive schema: `/api/docs` (non-production).

## Conventions

**Auth.** `Authorization: Bearer <accessToken>` from `POST /auth/login` or `/auth/register`. Tokens
last `JWT_EXPIRES_IN` (default 7 days) and are revoked immediately on password change/reset,
`POST /auth/logout-all`, deactivation or role change. The user's role is always read from the database.

**Errors** — every failure has the same shape:

```json
{ "statusCode": 409, "error": "Conflict", "message": "Sorry, that time is fully booked…",
  "path": "/api/reservations", "requestId": "…", "timestamp": "…" }
```

`message` is a string or, for validation failures, a list of strings. Status codes: 400 invalid input or
disallowed state change · 401 not signed in / bad token · 403 signed in but not allowed · 404 not found
(also used when a record exists but belongs to someone else, so ids can't be probed) · 409 conflict
(duplicate, already booked, record changed concurrently) · 413 too large · 415 not an image ·
429 rate limited / account temporarily locked · 503 database unavailable.

**Unknown fields** in request bodies are silently dropped — clients may send whole objects, but only
documented fields are ever written.

**Pagination.** `?page=1&limit=20` → `{ <items>, total, page, pages }`.

**Request ids.** Every response carries `X-Request-Id`; include it when reporting problems.

## Roles

| Role | How | Can |
|---|---|---|
| customer | `POST /auth/register` | browse, book, order, review, manage own profile |
| owner | `POST /auth/register-owner` | everything for **their one restaurant**: profile, menu, tables, bookings, orders, staff, inventory, promotions, analytics, billing statement |
| admin | server CLI `npm run admin:grant -- email` | everything, on every restaurant, plus `/admin/*`; every admin change is audit-logged |

Ownership is checked on every record (menu item → restaurant → owner, etc.), never taken from the client.

## Endpoints

### Auth `/auth`
| | | |
|---|---|---|
| POST | `/register`, `/register-owner` | `{ fullName, email, password, phone?, referralCode? }` → `{ user, accessToken }`. Password ≥ 8 chars with a letter and a digit. 409 if the email exists. |
| POST | `/login` | `{ email, password }` → `{ user, accessToken }`. 5 wrong passwords lock the account 15 min (429). |
| GET | `/me` | current user |
| PATCH | `/change-password` | `{ currentPassword, newPassword }` → `{ accessToken }` (other sessions are signed out) |
| POST | `/logout-all` | revoke every token |
| POST | `/forgot-password`, `/reset-password` | email link flow (`{ token, password }`) |

### Restaurants `/restaurants`
| | | |
|---|---|---|
| GET | `/public?search&cuisine&city&country&priceRange=$,$$&service=delivery\|dine_in\|pickup&minRating&sort&page&limit` | active restaurants |
| GET | `/public/featured`, `/public/cuisines`, `/public/stats`, `/public/:id` | public views (sponsored first in featured; `openNow` computed in the restaurant's time zone) |
| GET | `/my-restaurant` | owner |
| POST | `/` | owner creates their restaurant (one per owner) |
| GET/PUT | `/:id` | owner of it / admin |

Restaurant fields include `timezone` (IANA, e.g. `Africa/Kigali`), `openingHours` (`{ monday: { open: "10:00", close: "22:00", closed: false }, … }`; `close` earlier than `open` means past midnight), `dineIn/delivery/pickup`, `acceptingOrders`, `deliveryFee`, `minOrder`, `taxRate` (0–0.4), `prepTime`, `images`, `logo`.

### Menu `/menu`
Public: `GET /restaurant/:restaurantId` (categories with available dishes), `/categories/:restaurantId`, `/items/:restaurantId?categoryId`, `/item/:id`, `/popular`, `/search?q`. A signed-in owner/admin also sees unavailable dishes.
Owner: `POST /categories {name, sortOrder?}`, `PUT/DELETE /categories/:id` (delete only when empty), `POST /items {categoryId, name, price, description?, image?, tags?, isAvailable?, isSoldOut?, preparationTime?}`, `PUT /items/:id`, `PATCH /items/:id/toggle`, `DELETE /items/:id`.

### Images `/uploads`
1. `POST /uploads/image` (multipart field `file`) or `/uploads/images` (field `files`, ≤ 10) →
   `{ id, url, filename, mimetype, size }`.
2. Put the returned `url` on the record (`menu item.image`, `restaurant.images/logo`, `profile.avatar`).

Rules: JPEG, PNG, WebP or GIF, checked by file **content** (renamed files are rejected with 415); max
`MAX_UPLOAD_MB` (413). Names are generated by the server. A record only accepts images uploaded by the
same user (admins: any). When a record stops using an image, the file is deleted automatically if
nothing else uses it. `DELETE /uploads/:id` — uploader or admin; refused with 409 while the image is in
use; admins may add `?force=true` to detach it everywhere first. `GET /uploads/mine` lists your files.
Files are served from `/uploads/<name>` with `nosniff` and a sandboxing CSP.

### Tables `/tables` (owner/admin)
`GET /restaurant/:id`, `GET /floor-plan/:id`, `POST / {tableNumber, capacity 1–30}`, `PUT /:id`,
`PATCH /:id/status {status: available|occupied|reserved|blocked}`, `DELETE /:id` (refused while the table has upcoming bookings). Blocked tables are not offered for online booking.

### Reservations `/reservations`

**Booking workflow**

1. `GET /availability?restaurantId&date=YYYY-MM-DD&guests` (public) → `{ closed, slots: [{ time, available }] }` in 30-minute steps, in the restaurant's local time.
2. Customer `POST / { restaurantId, date, time, guests (1–20), notes?, phone? }` → reservation, `status: pending`, table assigned (smallest that fits) or seats counted against `seatingCapacity` when the restaurant has no tables.
3. Owner sees it: `GET /restaurant/:id?date&status&upcoming=true`, dashboard, notification.
4. Owner `PATCH /:id/confirm` (or `/:id/status {status, reason?}`), then `/:id/arrived`, then `completed` / `no_show` on the day.
5. Customer sees the status in `GET /my-reservations` and a notification.

Rules: not in the past, ≥ 30 min ahead, ≤ 90 days ahead, within opening hours (last seating 1 h before
close), on the 30-minute grid; a booking occupies its table for 90 minutes; one overlapping booking per
customer per restaurant; ≤ 10 upcoming bookings per customer.
Transitions: pending → confirmed|cancelled; confirmed → arrived|no_show|cancelled|completed; arrived →
completed. Customers may only cancel (`PATCH /:id/cancel {reason?}`) or reschedule (`PATCH /:id {date?, time?, guests?, notes?}` → back to pending).

### Orders `/orders`

**Ordering workflow**

1. Customer `POST /quote` to preview totals, then `POST /` with
   `{ restaurantId, items: [{ menuItemId, quantity (1–50), notes? }], orderType: delivery|pickup|dine_in, paymentMethod: "cash", deliveryAddress? (required for delivery), tableId? (dine-in), promoCode?, tip?, notes? }`
   and an `Idempotency-Key` header (8–64 chars) — repeating the request returns the same order.
2. The server looks up every dish and price, applies promotions/vouchers, and computes
   `subtotal − discount + deliveryFee + serviceFee + tax + tip = total`. Any price or total sent by the
   client is ignored.
3. Owner sees it in `GET /orders?status=active` (kitchen), `/orders/stats`, dashboard, notification.
4. Owner `PATCH /:id/status {status, note?}`: placed → confirmed → preparing → ready →
   (out_for_delivery, delivery only) → delivered. Any active order can be cancelled by the restaurant;
   the customer can `PATCH /:id/cancel` while it is placed or confirmed.
5. Customer follows `GET /:id` / `GET /my-orders?status=active|past` and notifications.

`paymentMethod: "card"` is refused (400) until an online payment provider is integrated — there is no
simulated card charge. Payment records: `GET /payments`.

### Other resources
- Reviews `/reviews`: public `GET /featured`, `/restaurant/:id`; customer `POST { orderId | reservationId, rating 1–5, comment? }` (once per completed order/visit), `DELETE /:id`; owner `PATCH /:id/reply { reply }`; admin can delete any.
- Promotions `/promotions`: public `GET /featured`, `/active/:restaurantId`; owner CRUD with `{ name, discountType: percentage|flat, discountValue, startDate, endDate, minOrder?, usageLimit?, applicableCategories?, code? }`. Promotions **without a code apply automatically** at checkout (best eligible one); coded ones need `promoCode`.
- Loyalty `/loyalty` (`GET`, `POST /redeem {rewardId}`), referrals `/referrals` (`GET`, `POST /invite {email}`), notifications `/notifications`, favourites/addresses/cards `/users/*` (cards: display data only — `last4`, `brand`, `expiryMonth`, `expiryYear`; full card numbers and CVVs are rejected), support `/support` (`POST {subject, description, type}`, `GET /my-tickets`, `GET /:id`, `POST /:id/reply`).
- Staff `/staff`, inventory `/inventory`, analytics `/analytics/restaurant/:id/{dashboard,overview,heatmap}` — owner/admin.
- Health `GET /health`; public settings `GET /settings/public` (currency, service fee, plans).

## Money: how the platform earns

All configurable at runtime with `PUT /admin/settings` (admin) — nothing is hard-coded:

| Stream | Who pays | When it is recorded |
|---|---|---|
| **Commission** — % of food sales after discounts (Starter 15%, Pro 10%, or a negotiated per-restaurant rate) | restaurant | order delivered |
| **Service fee** — % of the food subtotal, optional cap | customer (on the bill), owed by the restaurant that collected it | order delivered |
| **Booking fee** — per guest | restaurant | reservation completed |
| **Subscription** — monthly plan fee (Pro: lower commission) | restaurant | `POST /admin/billing/run-subscriptions` each month |
| **Sponsored placement** — listed first in featured, per week | restaurant | `POST /admin/restaurants/:id/sponsorship {weeks}` |

Each entry is written once per source into a ledger (`platformcharges`). Owners see what they owe in
`GET /billing/my-statement?period=YYYY-MM`. Admins: `GET /admin/revenue?from&to`, `GET /admin/charges`,
`POST /admin/charges/mark-paid {ids | restaurantId+period}`, `POST /admin/charges/:id/void {reason}`,
`PATCH /admin/restaurants/:id/billing {plan, commissionRate?}`, `POST /admin/billing/reconcile` (re-creates any
missed entry; idempotent). Cancelling a delivered order through `POST /admin/orders/:id/correct` voids its charges.

## Admin `/admin`
`GET /stats` · `GET /users?role&isActive&search` · `PATCH /users/:id {isActive?, role?: customer|owner}` ·
`GET /restaurants?status&search` · `PATCH /restaurants/:id/status {status, reason}` · billing routes above ·
`GET /orders`, `POST /orders/:id/correct {status: delivered|cancelled, note}` · `GET /reservations` ·
`GET /uploads` · `GET|PUT /settings` · `GET /support`, `PATCH /support/:id {status?, priority?}` · `GET /audit-logs?action&actorId`.

## Consistency

The API works on a standalone MongoDB (no multi-document transactions), so correctness under concurrency
comes from atomic single-document writes and unique indexes:

- **Double booking**: each booking claims one lock document per 30-minute slot and table (or a seat
  counter per slot for restaurants without tables) under a unique index — two simultaneous requests for
  the last table cannot both succeed.
- **Checkout**: vouchers and limited promotions are claimed with conditional updates before the order
  is written, and released if anything later fails; `Idempotency-Key` makes retries safe.
- **Status changes** are conditional on the status that was validated, so racing updates cannot both apply (409).
- **Reviews** are unique per order/visit; ledger entries unique per source.
